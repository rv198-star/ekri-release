# EKRI

**让 AI 先查项目，再动代码。**

EKRI 用来帮助 AI 长期理解一个已有软件项目。

它会把项目里反复需要确认的信息整理成一份可复用的工程知识，让 AI 不必每次接到任务都从头搜索整个代码库。

你可以把它理解成一份**跟着代码一起更新的项目速查表**。

当前版本：**v1.1.0**

## 它解决什么问题

在一个维护时间较长的项目里，AI 很容易遇到这些问题：

- 每次新会话都重新搜索项目入口、模块和调用关系；
- 不知道项目已经有类似实现，又写出一套新的；
- 接手旧项目时，不清楚哪些代码最重要、哪些地方不能随便改；
- 做重构时，只看到了几个文件，却不知道还有哪些使用方会受影响；
- 几个月前得到的项目理解已经过期，却仍被当成当前事实；
- 搜索没有找到结果，就误以为项目里不存在对应能力；
- 为了回答一个小问题，读取了大量其实无关的源码。

EKRI 的目标不是替 AI 写代码，而是先让 AI 对项目有一份更可靠、更省上下文的长期认识。

## EKRI 会帮 AI 记住什么

EKRI 重点整理这类信息：

- 项目主要由哪些部分组成，各自负责什么；
- 项目已经有哪些能力和现成实现；
- 关键代码、配置、资源和接口在哪里；
- 哪些地方存在依赖关系；
- 哪些代码由谁负责或与哪些职责有关；
- 哪些内容仍在使用，哪些只是兼容或历史遗留；
- 项目发生变化后，哪些已有知识可能需要重新确认；
- 一条结论来自哪里，是否已经确认，是否仍有疑问或冲突。

EKRI 不要求一次把整个项目全部读完。AI 可以先查最相关的信息，只有需要时再继续向源码和证据展开。

## 在一个已有项目里怎么用

### 1. 单独安装 EKRI

推荐把 EKRI 放在业务项目之外，不要把 EKRI 源码复制进你的项目仓库。

```bash
git clone https://github.com/rv198-star/ekri-release.git ~/.local/share/ekri
cd ~/.local/share/ekri
git checkout v1.1.0
```

下面假设你的项目在：

```text
/workspace/my-project
```

### 2. 第一次接入时，先确认项目版本

```bash
python3 ~/.local/share/ekri/EKRI/scripts/validate_observation_boundary.py \
  --repository-root /workspace/my-project \
  --target-ref HEAD
```

这一步会确认 EKRI 当前观察的是哪一个 Git 版本，并排除 EKRI 自己的运行文件，避免把扫描工具本身混进项目知识里。

如果只是想检查、不写入项目运行状态，可以加：

```bash
--no-write
```

### 3. 如果项目已经有 EKRI 知识，先验证再使用

项目可能已经保存了：

```text
.EKRI/project/<asset-id>/
```

这时不要重新扫描整个项目，先验证已有知识：

```bash
python3 ~/.local/share/ekri/EKRI/scripts/manage_project_assets.py verify \
  --repository-root /workspace/my-project \
  --asset-id <asset-id>
```

验证通过后，AI 应优先使用已有知识，只对缺失、过期或有冲突的部分重新查看源码。

### 4. 按问题逐步查询

例如，在准备增加一个功能前，可以先问：

- 项目里是否已经有类似能力？
- 现有实现在哪里？
- 哪些地方正在使用它？
- 这条结论依据什么？

已有能力查询可以使用：

```bash
python3 ~/.local/share/ekri/EKRI/scripts/query_capability.py \
  --repository-root /workspace/my-project \
  --source-tree <git-tree> \
  --query-kind find-capability \
  --query "你要查找的能力"
```

找到对应能力后，还可以继续查询实现位置、依据和相关信息，而不是马上重新搜索整个仓库。

> 注意：不同类型的项目知识需要不同的输入。EKRI v1.1.0 还不是一个“一条命令自动读懂任何项目”的工具。它更适合由 AI 根据当前任务选择需要补充的知识。

## 和 AI Skills 一起使用

如果你的 AI 开发环境支持 Skills、Rules 或项目级指令，可以让自己的 Skill 把 EKRI 当成一个外部项目查询工具。

**不要把 EKRI 整个复制进 Skill，也不要让 Skill 每次先全库扫描。**

建议在处理已有项目的 Skill 中加入类似规则：

```text
处理已有项目时：

1. 先确认目标 Git 版本。
2. 如果项目已有 .EKRI/project，先验证并复用。
3. 在大范围读取源码前，先查询 EKRI 已有知识。
4. 只有知识缺失、过期、有冲突，或当前任务确实需要时，才继续读取更多源码。
5. 搜索没有找到结果，不等于项目里不存在。
6. 新发现的项目结论必须保留来源，不能只凭文件名、调用关系或猜测升级成事实。
7. 当前任务需要的信息已经足够时，停止继续扩大扫描范围。
```

这样，Skill 负责当前任务，EKRI 负责保存和复用项目知识。

### 当前 Skills 支持状态

**v1.1.0 还没有提供一个官方通用的 `SKILL.md` 安装包。**

现在推荐的方式是：

```text
你的 AI Skill
    ↓ 调用
EKRI 命令 / Python 接口
    ↓ 读取和更新
目标项目的 EKRI 知识
    ↓ 必要时再回到
目标项目源码
```

未来如果提供官方 Skill，也应该保持这个边界：Skill 负责告诉 AI 什么时候使用 EKRI，而不是把 EKRI 本身变成一套固定的项目开发流程。

## 常见使用场景

### 接手一个陌生项目

先建立项目版本和基本知识，再逐步了解主要组成、已有能力、重要依赖和不确定区域，减少漫无目的地翻代码。

### 开发新功能

在生成代码前先查项目是否已有相同或相近能力，优先复用或扩展现有实现。

### 修 Bug

先定位相关能力、实现位置和依赖范围，再决定需要继续展开哪些源码。

### 重构或接手旧模块

先确认实现、使用方、依赖、维护状态和已有约束，避免只看局部代码就开始移动或合并。

### 项目持续演化

项目代码变化后，不必每次重建全部知识。EKRI 可以保留已有知识，并明确哪些内容仍可复用、哪些需要重新确认。

## EKRI 不会替你做什么

EKRI 不会因为扫描到了几个文件就自动决定：

- 这段代码可以安全删除；
- 两套实现一定应该合并；
- 某个人或模块一定拥有某项职责；
- 搜索没找到就证明某项能力不存在；
- 当前项目已经被完全理解；
- 某次重构已经安全可发布。

这些仍然需要结合当前任务、源码、测试和实际工程判断。
